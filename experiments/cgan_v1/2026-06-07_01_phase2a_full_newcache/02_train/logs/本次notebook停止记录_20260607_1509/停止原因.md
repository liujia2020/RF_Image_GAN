## 停止原因

`train.ipynb` 进入 Cell5 后运行约 9 分钟，仍未完成 epoch 1，`metrics/stability.csv` 没有写出首行。

观察到：

- notebook kernel GPU 占用约 3.4GB；
- GPU utilization 约 6%~8%，训练计算没有吃满 GPU；
- 两个 DataLoader worker 均接近 100% CPU；
- 两个 worker RSS 分别约 20GB~21GB；
- 系统 available memory 仍约 38GB~40GB，未被 OOM kill；
- 没有 loss NaN/Inf 记录，因为尚未完成 epoch 汇总；
- 没有 checkpoint、speckle_check.csv、snapshot 图。

判断为：`num_workers=2` 在当前数据形态下产生严重数据加载/预取瓶颈。每个 batch 的 `input` 张量非常大，reader 又会在 fp32 中还原真实幅值，worker 预取会复制巨大张量，导致 CPU/内存压力高、GPU 等数据。

## 处理

为避免继续空耗和扩大内存风险，Codex 手动停止了 nbconvert / ipykernel / DataLoader worker 进程。

停止后：

- 无残留训练进程；
- GPU 训练显存释放；
- 系统 available memory 恢复到约 53GB；
- 陈旧 `train.lock` 已移动到本目录保存。

## 给 Claude/决策侧的事实

本次没有完成正式 50 epoch，不产生 Phase2a 训练健康结论。

需要决策的点：

- 之前 `num_workers=0` 能进入正常训练并完成多个 epoch，但速度仍较慢。

建议由 Claude/用户决定是否允许把 `num_workers` 改回 `0` 或重新设计 batch/reader 传输方式。本记录只报执行事实，不做 PASS/FAIL 判定。
