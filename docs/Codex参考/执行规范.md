# 验证规则与项目纪律

最后更新: 2026-06-06

## 运行组织

每个正式运行按三个阶段组织：

```text
experiments/<track>/runs/<YYYY-MM-DD_short_name>/
├── 01_config/          训练前配置 (README / config.yaml / manifest)
├── 02_train/           训练产物 (checkpoints / probes / logs / loss)
└── 03_validate/        验证结果 (nii / figures / metrics / verdict)
```

每次实验应能回答：

- 在测试什么想法？
- 哪个模块/改动实现了它？
- 唯一的自变量是什么？
- 运行了什么 smoke test？
- 用了什么训练配置？
- 训练中有什么探针图像/指标可供检查？
- 最终汇总在哪？

## Smoke Test

Smoke test 只回答：

- 代码能跑吗？
- 有 NaN 吗？
- 有 OOM 吗？
- 判别器或生成器是否立刻崩溃？

Smoke test 永远不能证明质量。

## 大规模数据处理铁律

凡是处理超过 100 个文件或预计耗时超过 5 分钟的任务，强制执行两步流程：

**第一步：点火测试**
- 先拿 3~5 个文件跑脚本，确认语法正确、输出格式符合预期。
- 检查是否有 NaN/Inf、shape 错误、字段缺失等。
- 任何时候不得跳过这一步直接全量跑。

**第二步：全量执行**
- 点火测试通过后才可全量跑。
- 全量跑时必须输出进度（每 N 个文件报一次），输出写入日志文件方便随时查看。
- 全量跑完后必须校验结果完整性（数量是否对、有无遗漏）。

这步不是为了证明正确，是为了不浪费所有人的时间等一个语法错误的脚本。

## Phase2a 健康检查

Phase2a 只检查损失设计的健康：

- 稳定性
- 对抗平衡
- 指标不崩溃
- 没有明显模式坍塌
- 散斑形态大致合理（无结构承诺）

只有 Phase2a 验证通过、cache 干净且诊断表明散斑方向正确后，才能推进到后续阶段。

## 探针输出

每次 Phase2a 运行必须产出：

- 每 N 步的 B-mode 探针图像（固定 slice/固定角度/固定窗宽窗位）。
- 对应步骤的 DAS 对比图像。
- G 和 D 的损失曲线。
- 包络 L1 曲线（去归一化后）。

探针让人类能判断散斑形态是否在朝 DAS 方向走，而非仅依赖损失数字。

如果 Claude 发来的指令与本文档或 \ 中的规则冲突：

1. **以项目文档为准执行**
2. **把冲突点明确报出**：哪个指令的哪句话，与哪条文档规则不一致
